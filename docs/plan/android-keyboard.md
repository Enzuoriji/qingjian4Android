# 安卓：完善键盘

2026-09-18 定。安卓键盘现在是**最小可用**：点得准、能选词、能切中英，但「手感层」几乎是空的。
这份排的是「从能用 → 能日常用」。引擎那一侧见 [android-engine.md](android-engine.md)。

设计与取舍见 [../design/keyboard.md](../design/keyboard.md)（那里有「为什么只参考不抄」与手感清单）。

**工期口径**：半天 / 一天，指「写完 + 在设备上验过 + 有自动化测试」，按这一轮的节奏估。不是日历天。

## 现状

**键**：7 种——`Letter` / `Shift` / `Backspace` / `Mode` / `Space` / `Comma` / `Enter`
（`crates/qingjian-render/src/keyboard/key.rs`），三套布局：字母 / 数字 / 符号（`KeyboardLayout::of`）。

**手感与编辑手势**（一、二两组与 K6 / K7 已做完，2026-09-20）：

| | 状态 |
|---|---|
| 数字 / 符号面板 | ✅ 左下角 `符` / `123` 两页（数字页与符号页互为入口），`返回` 回字母页 |
| 震动 | ✅ **六档可选**（关 / 轻微 / 清脆 / 低沉 / 双击 / 自定义毫秒，设置页「键盘」那组）：除自定义外都走**系统的预置触感**，厂商按自家马达调过（E7，2026-09-22）。候选条那一按不震 |

| 取角标 | ✅ **长按字母键弹 `[大写][符号][小写]` 三格**（2026-09-21，照搜狗那套）——原先的「键上滑动」真机快打会误触，撤了 |

| 无障碍 | ❌ 读屏（K11，押后到引擎那边处理完） |

## 为什么差这么多

它是**原生 View 拼的键盘**：每个键一个 View，长按 / 滑动 / 连击 / 气泡 / 震动都是 Android 框架
自带或几十行挂上去的。我们是**自绘位图**：每个手势都要自己写状态机、自己画、自己算命中，
**成本高一个量级**。这是当初选自绘时就知道的代价（`docs/design/keyboard.md` 记了理由）。

滚动重绘那条差距（它只重画按下的那一个键，我们整块重画 + 过 JNI 传 2.3 MB）**这一轮不动**：
实测按下 2–4 ms、抬起 2–5 ms（模拟器、release），够用。等键盘上加了面板 / 动画再说。

## 一、先让它打得出东西（1.5 天）

### K1 数字 / 符号面板 —— 1 天

**做什么**：
1. 加两套布局（数字 `123…`、符号 `？！：；（）@#…`）与一个切换键
2. `KeyId` 加 `Digit(char)` / `Symbol(char)`（或统一成 `Literal(char)`）
3. 中文标点转全角——`Engine::punctuate` 已经能转，接上就行

**为什么排第一**：这是**功能缺口**不是打磨。现在打不出数字和标点。

**渲染器不用改**：`KeyboardLayout` 本来就支持任意行数与键宽，`render_keyboard` 按行画。

**验收**：
- 宿主机测试：切到数字页后键帽数与内容对；点 `？` 上屏全角「？」
- 设备截图：三个面板来回切

**要定的**：切回去之后停在字母页还是记住上次的页？（建议切回去就回字母页，跟主流输入法一致）

### K2 震动反馈 —— 半天

**做什么**：按下时 `performHapticFeedback`。我们已经有按下 / 抬起事件（`Session::touch` 的
`MotionAction::Down` / `Up`），插进去就行。

**为什么**：**最便宜的手感提升**。而且震动是「按到了没有」的主要反馈——自绘键盘没有原生
`state_pressed` 的即时感，手感落差很大一部分在这。

**验收**：手上有反馈；后续要能关（跟 E7 的配置一起做）。

**注意**：`HapticFeedbackConstants` 在安卓上分得细（`KEYBOARD_TAP` / `LONG_PRESS` / `VIRTUAL_KEY`），
选适合输入法的那个；部分机型要 `FLAG_IGNORE_GLOBAL_SETTING` 才有反应。

## 二、手感（3 天）

### K3 长按退格连删 + 按住连发 —— 1 天

**做什么**：长按计时器（`Session` 里加一个「按住的目标 + 按下时刻」），到时按固定间隔重复触发 `Act`。
退格键设为可连发；顺带把「长按」这个能力留成通用件，K4 / 后面的键都用得上。

**为什么**：改错字现在只能一下一下点。

**验收**：按住退格 1 秒能连删十几个；抬起就停。

**注意**：计时器在 Rust 侧还是在 Kotlin 侧？Rust 侧要引线程 / 定时器，Kotlin 侧有现成的
`Handler.postDelayed`。**建议 Kotlin 侧计时、回调 `touch` 一个「重复」动作**——简单、也不用给
Rust 引运行时。

**2026-09-20 已做**，落在两处：

- **计时在壳**（`QingjianSurfaceView`）：`downAt` 记每根手指按下的时刻，一个 `Runnable` 每 50ms
  把按够 300ms 的手指各报一次，回调 `QingjianNative.repeat(handle, pointer)`。
  松手 / `ACTION_CANCEL` 撤掉。**按根记**，不是全局一个「按住的键」——两根手指交替时后者会挤掉前者。
- **判断在 Rust**：`Session::repeat(pointer)` 问 `Keyboard::held(pointer)` 拿到那根手指按着的键，
  再看 `action::repeats(key)`（**只有退格**）。壳不知道哪个键会连发。

两条计划里没写、做的时候才撞上的：

- **连发过的，抬起不再补一下**。键是抬起才兑现的，按住删一串之后松手那下会再删一个——
  每次都要多退一格。`Press` 加了个 `repeated` 标记挡掉。
- **验收实测**：`ni'hao'ma` 按住退格 600ms 剩 `ni'h`——当时门槛是 400ms，正好 (600−400)/50 = 4 个；
  松手不再多删。截图见 `screenshots/2026-09-20_长按退格连删_*.png`。
  （门槛后来调到 300ms，同样按住 600ms 会删到 6 个。）

**没做**：加速连发（按住越久越快）。硬件键盘有，这里先按固定 50ms 来，手感反馈了再说。

### K4 取角标（长按弹选项）—— 1 天

> **⚠️ 现在做的是「长按弹选项」，不是滑动**（2026-09-21 换的，见本节末尾「K4 的遗留」）：
> 长按字母键弹一排 `[大写][符号][小写]`，默认停在符号，左右滑着选、松手输入。
> 下面 146–167 行那段**滑动手势**的来龙去脉留着当事后记录看，**别再照着它实现**。

**做什么**：手指在键上上下滑出另一个符号（比如 `，` 上滑出 `？`）。`MotionAction::Move` 已经有，
加「方向 + 阈值」就能判；渲染器要在键帽上画那个小角标。

**2026-09-20 做完了，来回改了三次，最终是「只认往下滑、阈值 22 点」。** 经过：

1. 一开始只认往下滑。
2. 用户说「快打时得特意朝下瞄、容易滑歪」→ 改成**四个方向都算**（径向距离）。
3. 真机上**快打误蹦符号**。先试把阈值 12 → 16 点（提交 `4be40f5`），仍然误触。
4. 于是**收回成一个方向**（用户 2026-09-20 拍板「仅往下吧」）。最终 `SWIPE = 22.0`。

**为什么收回是对的**（不是退回去将就，是两条改善叠加）：

- **横向那条路结构上就救不了**：「手指出了键 = 这一下作废」与手势阈值线是**重合**的
  （都卡在半个键宽，约 15 点），阈值往上加只会变成「符号不出、字母也一起丢」。
- **误触面砍到四分之一**——只有「朝下滚」才可能撞上，往左右上滚一律不算。
- **纵向终于有空间了**：四个方向时阈值被半个键宽卡死；只留往下之后比的是**键高**
  （半步 21~27 点），才敢从 16 提到 22。
- **代价很小**：另外三个方向的角标字符在 `123` / 符 两页面板里都有，不至于打不出来。
  另外三个方向也不再是手势——挪得少就还是这个字母，挪出键外这一下作废。

**角标目前只挂在字母键上**（照参考图），要不要给 `，`、`123`、符号页也挂，是一行数据的事，还没定。

**~~还没验~~** ~~这一版（22 点 + 单向）只在宿主机上验过，真机复验待做~~ ——
**这一版已经不存在了**：真机上快打照样误触，2026-09-21 整个撤掉换成长按。
现在待验的是**长按那套的手感**，判据见下面的「K4 的遗留」。

**为什么**：数字 / 标点面板的补充——不用切页就能打常用标点。

**验收**：在逗号键上滑出「？」，直接上屏。

### K5 键预览气泡 —— 1 天

**做什么**：按下时在键上方弹一个放大的气泡显示这个键。自绘的话要渲染器再出一张小位图，
或者用安卓原生 `PopupWindow`（更省事，但那就不是「显示面自绘」了——**要定**）。

**为什么**：手指挡住键帽时，气泡是唯一的确认。

**2026-09-20 已做，路线定的是「自绘位图 + 浮动小窗承载」**：

- **气泡照样由 Rust 画**（`renderer/keyboard/popup.rs`），壳只把它贴到安卓的 `PopupWindow` 上、
  挪到 Rust 算好的位置。**「显示面自绘」那条线没破**——壳不参与画，也不做布局计算
- 不用「键盘上方留一条透明带」那条路：输入法窗口会盖住那条带，**既占屏幕又吃触摸**
  （点在键盘正上方会没反应），跟刚做的「候选条自动收起」正好相反
- 渲染器多出一个出口 `render_key_popup`；壳侧多一个 `KeyPopup`（就是个 `PopupWindow` 加一个 `ImageView`）
- 摆哪儿由 `Keyboard::popup_origin` 算：气泡**内容**的底边贴着键顶、水平正对键心；
  最左 / 最右那几个键气泡比键宽，往里**夹一下**不许探出屏幕

两个只有真机上才撞得到的坑：

- **`PopupWindow` 在输入法里能用**（AOSP 自己就这么干），但它是**输入法窗口的子窗**
  （`mParentWindow=InputMethod` + `INSET_PARENT_FRAME_BY_IME`），**坐标相对父窗、不是屏幕**。
  按屏幕坐标传（自己加 `getLocationOnScreen`）整块会跑到屏幕外面去
- 传的必须是**位图**的左上角，不是**内容**的：位图四周留着一圈阴影，忘了减就整体偏一个阴影宽

截图见 `screenshots/2026-09-20_键预览气泡_*.png`；设备实测气泡底边与键顶**像素级对齐**
（666..779 对 780、879..992 对 993）。

## 三、编辑与候选（3 天）

### K6 空格上滑动 → 移动光标 —— 半天

在空格键上左右滑，按位移量发左右方向键（`Command` 加 `MoveLeft` / `MoveRight`）。

**2026-09-20 已做**，当天按手感又改了一版（第一版「松手才走」用户当场说不好用）：
现在是**拖动当中就走、越拖越快**——越过死区 8 点开始，速度随位移线性涨到 40 格/秒；
死区以内仍然算「按空格」（上屏高亮候选）。
`Keyboard::touch` 的返回从 `Option<KeyId>` 换成 `Option<Fired>`——移光标不是「某个键」，
翻不成 `action::on_key`，得分开报。滑出空格键外也算数（空格键宽，划着划着就出去了）。
设备实测：`abc` 左移两格打 `x` 得 `axbc`，再右移一格打 `y` 得 `axbyc`。

**踩过一个坑**：第一版按计划写的那样发 `KEYCODE_DPAD_LEFT/RIGHT`，结果光标到头时
方向键没人消费、往上冒成**焦点导航**——在设置里滑空格，焦点会跑到返回 / 删除按钮上。
改用 `InputConnection.setSelection`（问 `getExtractedText` 拿到当前位置再算目标）后消失。
实测左滑 10 格（远超文本长度）光标停在开头、焦点仍在输入框里。

### K7 退格上滑动 → 选择 / 删除 —— 1 天

向左滑选择、继续滑删除选中。~~要发 `KEYCODE_DPAD_*` + `SHIFT`~~，
**这条写错了、别照做**：`KEYCODE_DPAD_*` 在安卓上是**焦点导航**用的，
选到头会把焦点挪到界面按钮上（K6 已经踩过）。

**2026-09-20 已做，但做的是另一个手势**：第一版照上面「往左滑选字、松手删选中的」做了，
**用户当场说不好用**，改成 **⌫ 上往上滑 → 松手把光标前面整段清掉**（滑上去只是预备）。
实现只用一条 `InputConnection.deleteSurroundingText(前面有几个字, 0)`。

顺带修了一个冲突：**手势一开那个键就不再算「按住」**（`Keyboard::held` 排掉），
不然滑得慢（超过连发门槛 300ms）会一边做手势一边被长按连发删。

### K8 候选条长按删候选 —— 已摘掉（2026-09-20）
长按候选删除（词库词清学习、用户词整删，`Engine` 有现成的删词接口，见 `candidate-ui.md`）。

**2026-09-20 做过一版，同日整个摘掉了，用户说「真的觉得它没什么用」。** 原委：

- **真机上不可能有效果**：删词走 `Engine::forget`，而**安卓壳从头就没接 `Learner`**
  （`Session::open` 只调了 `with_emoji`，引擎缺省挂的是 `NoLearner`），`forget` 永远返回
  「什么都没删」。纯词库词更冤——它本来就没有学习记录可清，接上 `Learner` 也删不掉，
  要真删掉得给引擎加「屏蔽词」，那是新功能。
  （**2026-09-22 补**：`Learner` 已经接上了，见 [android-engine.md](android-engine.md) 的 E1。
  但 K8 本身**不复活**——上面那条「纯词库词删不掉」的理由还在，而且用户当时就说过它没什么用。）
- **宿主那三条用例是虚的**：只断言了「有话要说」，三句提示（删了用户词 / 忘了学习 /
  词库里的词没有学习记录）里任何一句都算过，所以它们拦不住上面这件事。
- 反馈用的**系统吐司在真机上一句都没弹出来过**（厂商 ROM 拦吐司是常事），
  于是「没话说」和「说了但没看见」根本分不清——**别再往候选条上加依赖吐司的反馈。**

**留着不动的**：`Engine::forget` 是 Core 的接口，macOS（⇧ + 数字）与 Windows 还在用，没动它。
**当时顺带修掉的两处真 bug 都留下了**，它们与 K8 无关：①⌫ 上滑清空时 `clearing` 没排进
`sliding` 的豁免名单，手指出键气泡当场消失；②手势阈值从 12 点提到 16 点（快打误打符号）。

**不在这条线上**——它属于引擎那份：[android-engine.md](android-engine.md) 的 **E1 用户学习落盘**。
（2026-09-20 查 K8 时发现安卓壳没接 `Learner`，一度记在这里，属于记错地方：键盘计划只管手感与编辑手势，

### K9 键盘高度可调 —— 2026-09-20 做了一半（自适应）
**做了什么**：高度不再写死，按**屏幕当前方向那一维的比例**算——竖屏 30%、横屏 49%，
夹在竖屏 `[200, 300]`、横屏 `[170, 260]` 之间（`KeyboardTheme::fitted`）。
比例就是 fcitx5 那套，原先那两个定值 202 / 176 本来就是它按小屏手机换算出来的快照，
所以**大屏偏矮是定值法的必然**。当初不敢用百分比的理由（平板横屏八百点高会算出巨无霸）
用上限夹掉。壳报的是**竖屏长边 / 横屏短边**，不直接信 `displayMetrics` 的高度
（有的 ROM 转屏后还报竖屏那个值）。

验收在宿主机上（`session/tests.rs`）：大屏更高、平板被上限夹住、横屏仍矮一截。

**模拟器实测**（2026-09-20）：一台 AVD 上靠 `adb shell wm size` 换四种屏幕，从截图里量键盘高度
（按应用底色找键盘顶边），四个都与公式**分毫不差**：

| 屏幕（点） | 公式 | 实测 | 备注 |
|---|---|---|---|
| 360×640 竖屏 | 192 → 夹到 200 | **200** | 下限 |
| 360×960 竖屏 | 288 | **288** | |
| 540×1200 竖屏 | 360 → 夹到 300 | **300** | 上限 |
| 640×360 横屏 | 176 | **176** | |

前三张量出来的键盘顶边（784 / 1248 / 1704）与 `dumpsys window` 报的输入法窗口 frame 完全一致。
截图在 `screenshots/2026-09-20_键盘高度自适应_*`。

**顺带发现一个没查清的**：横屏下输入法**窗口**的 frame 比画出来的键盘高约 97 点
（窗口从 y=77 起、键盘从 y=271 起），那一带应用从底下透出来。竖屏两者严丝合缝。
键盘本身是对的（行高也对得上：每行约 70px 正是 176 点该有的），但那一带**是否吃触摸**没测——
真要是吃，横屏上紧贴键盘上方约 97 点会点不动。**留待确认**，与这次改动无关（改之前窗口也是这么大）。

**还没做**：**手动调**。用户选了「先自适应」，手调要等有设置界面——
那属于引擎那份的 **E7 配置**（设置界面按架构约定要用原生控件，不是一个键盘里的手势能替代的）。
真要给键盘加手势调高度，得先想清楚手势占哪儿：字母键**往下**被取角标占了、空格被拖光标占了、
⌫ **往上**被清空占了——没有一块现成的地盘。
（不过 K4 改成单向之后，字母键的**其余三个方向空出来了**，将来要加手势可以从这儿挑——
前提是那个手势的误触风险比取角标低，别再走一遍「四方向 → 误触 → 收回单向」的老路。）

### K12 候选条收尾 —— 已做完（2026-09-21）

候选条 2026-09-21 改成一条能跟手横滚的带子，当天做完三件：

1. ~~**页码的语义**~~ **已做（2026-09-21 晚）**：原先是**窗口**的序号（一个窗口 24 个候选），
   跟「看得见哪一段」对不上——`shi` 显示 `1/21`，滑半天数字不动（用户报的）。
   现在整条候选一次铺开（`BarStrip`）、`scroll` 是整条的位移，页码是**第几屏 / 共几屏**、跟着手指走，
   `‹ ›` 一次滚一屏。设计见 `docs/design/keyboard.md`，实现要点见 `docs/notes/crate-notes.md`。

2. ~~**惯性**~~ **已做（2026-09-21）**：甩一下松手，带子接着滑一段再慢慢停下。
   分工照旧「节拍在壳、手感在 Rust」：壳用安卓自带的 `VelocityTracker` 量抬手速度报上来，
   一帧 16ms 自己排（另开一条 `flingTicker`，不动连发那个 50ms 的心跳），
   衰减曲线与「甩不甩」的判据在 `session/fling.rs`。
   **帧开销实测**：一次甩动约 150 帧，只有 1 帧超过 16ms（22ms，模拟器），
   其余都在预算内——所以「复用同一张 Bitmap」那条优化先不做。
   截图见 `screenshots/2026-09-21_候选条惯性_*.png`（3/82 → 7/82 自己滑、慢拖停在原地）。

原先这两件的估算与顾虑（留档）：

- 页码那条原以为要按可见范围算，实际做下来是**整条候选铺开**（要量几百个词的宽度，可接受）
- 惯性原以为要「另加一条更快的通道」，实际是在视图上再排一条 16ms 的 `Runnable`：
  壳只负责敲帧、问一句「这一拍走多少」，走多少由 Rust 按「过去多久」积分算

### K4 的遗留：真机验收（2026-09-21 换过机制，验收点也变了）
「在键上滑动取角标」真机上快打仍会误触，**已整个撤掉**，改成长按字母键弹一排选项
（`[大写][符号][小写]`，默认中间符号，左右滑选、松手输入）。机制上误触面归零——
长按是有意的动作，快打够不到 300ms。真机要验的是**手感**：0.3 秒等不等得及、
三个格子滑起来准不准。

## 五、收尾（4.5 天）

### K13 面板完善 —— 3 天（2026-09-22 用户提的，排在这批的最前面）

**为什么排最前**：这两件都是「用户天天要用的入口差一口气」——候选条看不见全部候选，
表情分类只能一下一下点箭头翻。

**① 展开选词 —— ✅ 完成（2026-09-23，2 天，模拟器上验过）**

现在候选条是**一整条跟手横滚**（一屏看得见三到六格，多的靠滑和甩）。滑动本身很顺，
但**少一个「一屏看全部」的入口**——想找第三屏那个词，得一直滑。

参考项目 fcitx5-android 走的是另一条路：候选条**不滚**，满了就收，多的进一个展开面板。
我们的取舍是留着滚动（更跟手），只补那个面板。

- **入口**：候选条上**长按**（原来的「长按 = 慢慢点一下」就此作废）。右端已经有 `×` 和
  `‹ ›` 三块，再加一个入口太挤；而长按在候选条上本来就没用上（K8 那个「长按删候选」
  2026-09-20 摘掉了）。
- **样子**：**盖住键盘区**的一块多行网格（键盘让开、不是压缩它）——一屏铺三十来个，
  比候选条那一行多得多。格子**按内容分宽、一行排不下就换行**，与候选条**同一套量宽**，
  所以同一个词在两处一样宽、行高也一样。
- **点一个上屏**；**点候选条**、**按返回**、上屏之后都收起来。
- **能上下滚**：80 个候选一屏铺不下，跟手滚 + 甩动惯性（照剪贴板列表那套）。
- **上限**仍是 [`CANDIDATE_LIMIT`]（80 个）：高频音节能出几百个（`ni` 是 501 个），
  全铺出来要逐格量宽度，几十毫秒起步（见那个常量的注释）。

**落在哪**：渲染器新开 `renderer/panel/`（`CandidateGrid` 折行 + `RenderedPanel`），
与候选条共用三样东西——量宽 `bar_cell_widths`、画法 `draw_bar_row`、行高 `candidate_row_height`。
会话侧**面板占的是键盘那张位图**（`keyboard_surface` 在那儿分流），所以壳一行都没改：
还是「上面一条候选条、下面一张位图」，触摸照样按 y 分派。返回键是**新加的一条 JNI**
（`Session::dismiss`）：**返回 0 = 这一下不归输入法管**，壳照常把返回交给应用收起键盘。

**踩过的两个坑**（都不是写错逻辑，是「两块地方对不齐」）：

1. **面板底部被系统导航栏压住**。键盘位图的高度是 `theme.height + bottom_inset`——
   键只排到 `theme.height` 为止，底下那一段留给导航栏。面板照着 `keyboard_height()`
   （= `theme.height`）算就矮了一截，而候选铺满了整张图、伸进了那一段。
   两处一起修：高度按**键盘位图那么高**算（`keyboard_height() + bottom_inset`），
   候选画在一张**只有可用高度**的小图上再整张贴回来（画布自己不裁，与键盘剪贴板页同一个路数）。
2. **滚动上限不能从「等着重画的空位图」上问**。最初滚动时把 `expanded_view` 置空当脏标记，
   于是下一拍 `max_scroll` 返回 0、滚不动了。改成单独的 `expanded_dirty`：位图留着，
   上限从**这一帧的网格**上问（格子折行铺完才知道多高）。

验收：模拟器上敲 `qi`（12 屏候选）长按 → 面板铺开三十多个、上下滚得动、点一格上屏、
返回收起且**拼音还留着**（返回没有把键盘整个收掉）。截图在
`screenshots/20260923_展开选词_0*.png`。

**⚠️ 在模拟器上验之前先看这条**（2026-09-23 耗掉一个多小时的假象）：
**重装 APK 之后系统不会自动把输入法重新绑上**——键盘照样画得出来（视图在），
但触摸全被吞了：敲键没反应、候选条不动，**看着跟代码写坏了一模一样**。
先来一句 `adb shell ime set app.qingjian.android/.QingjianImeService` 再验
（重启模拟器后也要，那次会先报一句 `Unknown input method`，等系统扫完再执行一次就行）。
要确认是不是这个：`dumpsys input_method` 里 `mBoundToMethod=false` 且进程不在。

**② 表情分类横滑 —— ✅ 完成（2026-09-23，1 天，模拟器上验过）**

分类标签条原来是一行定宽格子（一屏 3 个分类）加两头 `‹ ›` 箭头翻页，**只能点、不能滑**。
现在两头的箭头去掉（`KeyId::EmojiGroupPage` 整个删掉），**整条都是分类、一屏五个**，
多的靠横滑看。

- 横滑照剪贴板那套竖滚的写法（`emoji_group_fling` / `emoji_group_scrolled` 与
  `clipboard_fling` / `clipboard_scrolled` 一一对应），`Fling` 直接复用。
- `Keyboard::touch` 的 `Move` 分支加横向判定，**排在纵向滚动之前**：同一页上标签行横着滑、
  格子区竖着滑，按方向认。**按行判不按格判**（`Keyboard::label_height()` 划边界），
  落在格子之间的缝里也能滑。
- `start_fling` 加第三路（`emoji_group_scrolled` 命中时走）：甩起来就滑一段，
  **没甩起来就就地吸附到整格**（`settle_emoji_groups`）。
- **滑动只换「看哪一段」，不换选中的类**——点一格才切过去，与候选条「滑是看、点才上屏」一致。

验收：一屏五个分类、横着拖跟手、甩一下自己滑一段（滑到末尾被夹住、不露空白）、
松手吸附到整格、滑过之后点第 0 格切到的是第二个分类。截图在
`screenshots/20260923_表情分类横滑_0*.png`。

（2026-09-23 白查了一轮：一度以为这次改动引入了回归，把改动 stash 了回退构建才发现不是）。
那是系统还没算好 insets 就绑上了，**重新唤起一次键盘就恢复**，不用管。
真正的坑还是上面那条 `ime set`，另外记一句：**单敲一次 `ime set` 不生效**——
它已经是默认输入法了，set 同一个等于没做；得先切到别的输入法再切回来，
`dumpsys input_method` 里的 `mBoundToMethod` 才会变 `true`。

### K14 剪贴板打磨 —— 1.5 天（2026-09-22 用户提的，排在 K13 后面）

清空要二次确认（完善），外加三个当前的问题。**四件都在同一片代码上**，
合成一次做比拆开省（读两遍同一段反而慢）。

- [ ] **清空的二次确认（半天）**：现在点「清空」**直接清光**，手滑一下就没了。
      改成点一下变成「再点一次清空」、**5 秒内**再点才真清；超时或者点了别处就退回原样。
      （键帽文字跟着换，图标位置不变。）
- [ ] **左滑删除没有提示（半天）**：「松手删除」那套气泡代码**就在那儿、也是好的**，
      但被 `keyboard.rs` 里一条早退挡住了：`if matches!(key.id, KeyId::Clipboard(_))`
      → `forget_popup(); return`。那条早退是 2026-09-21 用户要的（`c617652`：按住一条时
      气泡正好压在下面那几条上，想看别的就碍事）——**它说的是「平时」**，
      结果把「删除态」也一起挡了（那段早退在 `pressed_deleting` 分支**之前**返回）。
      于是删除态唯一的反馈只剩卡片按下时变个色，手指划过去根本看不出要干什么。

      **修法是加例外，不是推翻当初那条**：`&& !self.pressed_deleting`——
      平时照样不弹，只有手指往左划着、真要删的时候才弹那句「松手删除」。
- [ ] **清空之后又冒出来一条（半天）**：`onStartInputView` 每次键盘弹出来都会
      **无条件**把系统剪贴板里当前那条再记一遍（`readClipboard` → `clipboardChanged`），
      清空根本没挡住它。要在会话或壳那侧加一个「**刚清掉的就是系统剪贴板里这条，
      别记回来、直到它变了**」的标记。
- [ ] **带换行的条目显示成白框（半天）**：渲染器是**单行**设计，`\n` 从数据到画笔
      全程没人折叠——第二行被画到卡片外面（被裁掉），看着就是个白框。
      **按用户说的「多行的部分直接省略」**：只画第一行，后面不显示。
      现成参照：`qingjian-core` 的 `CustomPhrase::preview`（`custom_phrase.rs`）已经做过
      「`\n` → `↵`」这种单行化，修剪贴板时照同一处下手即可，不用动底层画笔。

**这四条都是一两行的局部改动**（除了二次确认要从键帽画到执行那条链），
所以真着急的话**半天能全清掉**——排在这儿只是按「完善优先」的顺序放。

## 风险

1. **自绘的代价会一直收**：每加一个手势都要自己写状态机 + 自己画 + 自己算命中。
   如果 K4 / K5 / K10 做下来发现成本失控，值得重新评估「键盘是否该改用原生控件」
   （候选条继续自绘）——那是个大决定，但趁早比晚了强。

   **2026-09-18 已把接缝切好**：键盘的布局、位图、命中与按下状态机都收进了 `apps/android/src/keyboard.rs`，
   `Session` 只通过几个方法跟它打交道（见 `docs/notes/crate-notes.md`）。于是两条路可以并排开发、丢掉哪条都只是删一处。
   判定走哪条不能凭感觉，看三个数：**同样做 K1 + K2 + K5 各花多久**、**主题要不要在 Kotlin 里重写一遍**、
   **多指快打还掉不掉字母**（最后一条是当初选自绘的原因，也是这次真正要比的）。时间盒 3 天，没结论就丢。
2. ~~**K5 的路线要先定**~~ **2026-09-20 定了**：自绘位图 + `PopupWindow` 承载，
   画还是 Rust 画、壳只挪窗，两边的好处都占（见上面 K5 那节）。
3. **K1 的中文标点规则**：全角 / 半角、成对引号、省略号……不是列个表就完事，
   要对齐 `docs/design/candidate-ui.md` 的按键规格。
4. **K11 是结构性短板**：自绘键盘做无障碍，成本远高于原生控件，别低估。
